The separate **OpenShock Hub** indicator remains green when the hub is online; that cannot confirm shocker power or RF reception. Pausing a Bluetooth toy does not change its connection color.

**Toy panel → Bluetooth toys** has one independent card per supported motor/function, using the shocker cards' three columns, 12-pixel gaps and 182-pixel compact height. Toy and shocker names share the same font; existing model positions are retained. The toy name and function are top-left. Input and Sensitivity sliders occupy the same bottom positions as the shocker sliders. Options/More is in the same position and expands to show a matching **Max %** slider, battery, **Read battery**, **Forget toy** and **Stop toy**. Setting Input to zero clears only that function; Stop toy clears all sibling functions. Unknown functions get an unavailable-controls card rather than a guessed motor. Local controls work independently of OpenShock tokens or bridge startup.

The second status row shows **Bluetooth**, **Ingame curve**, **Scan toys** and **Reset Bluetooth**. Click anywhere in Scan toys (except the help icon) to start/stop scanning; its state is Scanning or Inactive. Scans still finish automatically. Explicit Stop scan also pauses background discovery until a new scan or Reset Bluetooth. The eighth panel replaces the connected toy count: click it to stop toy activity, release the app's Bluetooth sessions and reconnect with fresh state. Saved sensitivity/maximums remain; Input returns to zero. Busy means another operation is still running. Bluetooth shows Active only when the native adapter is ready, or Simulated for test inventory. Ingame curve remains Inactive pending later main-app integration.

**Settings → Bluetooth toys** contains the source selector, **Updates/toy/sec**, **Reset Bluetooth**, **Stop all toys**, **Cancel operation** and diagnostics. Choose **Simulated toys** to try it without hardware, or **Simulated Bluetooth off** to check setup errors. Battery refreshes once after each connection and every five minutes per connected toy, shared by all its motor/function cards. Reads wait until scanning finishes; **Read battery** in Options refreshes immediately and restarts the interval. Unknown/failed readings wait five minutes before another automatic request. Unknown battery remains unknown, and 0% is valid. Local errors also appear on Log.

Toys connect automatically and healthy connected functions are ready for input. Each function has separate **Input** and **Sensitivity** dot sliders (0–100%), status, and a **Max %** slider under Options. Input changes output immediately through the shared scheduler: 0 is off and 100 requests full power, subject to Sensitivity and Max %. Connect, Disconnect, Auto-connect, Enable controls, Seconds and Run remain removed. Editing sensitivity/maximum while idle sends no output. A function holds its latest input until replaced, zeroed, stopped or disconnected; the old manual countdown is unused on this page. Sensitivity scales input, then the maximum clips it. Zero input/sensitivity/maximum is off. Sent shows the native step submitted successfully, not measured motor speed; Test mode shows Preview without actuator commands. Native discrete steps can round low percentages to off. SPS contact and calibrated socket-depth mappings are available in the SPS body map; real-avatar calibration and remote toy input remain pending.

**Stop toy** and **Stop all toys** clear current/pending activity. Controls return to readiness after zero completes and only a fresh input can restart them. Restart/reconnect starts idle; old values are never replayed. Explicit scanning, disconnect, source switch, test-mode transitions and app close stop app-owned activity. Background recovery scans wait while another function is active; after startup collection they do not repeat when all toys are connected. Stop bypasses ordinary pacing and is checked between normal writes. A native output/zero error requires recovery rather than automatically reopening output. Depth/position zero stops related thrusting instead of moving to endpoint zero. No rotation-direction, stroke-range or pattern controls are added here.

**Updates/toy/sec** in Settings defaults to 5 and accepts 1–10 for testing. All functions of a toy share that allowance, and all toys share a 20/sec normal-update ceiling. Ready different toys submit in groups of at most four, one ordinary command per toy, with fair turns and serial native calls. Each call reserves shared allowance from submission time, and the next group waits for the resulting allowance; a rolling window also caps normal writes at 20/sec. Idle time earns no credits. Only changed native values send, and the newest input is rechecked after transport waits. Slow call time counts toward pacing without another shared pause afterward; completed zeros add no new pause. Stop/expiry are checked between commands. The choice survives source switches/Reset Bluetooth during this session and defaults to 5 after reopening. These are unmeasured application ceilings; they do not establish this adapter's capacity. Settings diagnostics show waiting/submitting functions; hover over a function's state for details. **Wait** measures app delay before submission; **submit** measures pipe/library return time. Neither measures motor response or a hidden Bluetooth queue. Sent advances after successful submission return, and an already submitted/blocked call can still delay Stop.

Save **Settings → Debug → Test mode** off for real local output; saving does not require an OpenShock token. Configured OpenShock output still requires its own credentials at bridge startup. Sensitivity and maximum remain saved per installation key/function in versioned `%LOCALAPPDATA%/SzebsToys/local-toy-controls.json`; the old duration field is retained for compatibility. Input/activity are never saved or restored. Simulation is memory-only. Unreadable control settings are kept and prevent automatic output readiness until repaired. Physical output/stop remains unverified on hardware.

Startup discovers/connects nearby toys and reconnects remembered toys regardless of their old Auto-connect flags. Automatic scans connect found toys after a short advertisement collection period: 250 ms without another new toy, capped at 750 ms from the first candidate. Offline remembered toys do not hold up available toys. After a short search misses a known toy, follow-ups allow a full uninterrupted search of up to 15 seconds while output is idle. This preserves healthy connections and remains cancellable through Stop scan. Startup-only collection retains its budget; missing/failed toys and an empty radio retry after three seconds. These are app waits; native discovery/connection can still take longer. **Scan toys** remains a full explicit scan (up to 15 seconds); fresh discoveries connect after it ends, before searching again for any absent saved toy. Connected toys are remembered separately, including identical models. Offline rows remain selectable with unknown battery. **Forget toy** is available only offline: it deletes the saved entry and excludes that toy from automatic reconnection for this session. Turn the toy off and wait for Offline first. Reopen or Reset Bluetooth to rediscover it. Remembered data remains encrypted for your Windows account; simulation is session-only.

The native library runs in a hidden copy of this EXE. Lost sessions are released before rediscovery; loss/disconnect/failure refreshes the Bluetooth process on the next scan when no other toy is connected. **Reset Bluetooth** stops/releases all local toy connections, starts a fresh Bluetooth process and discovers/connects automatically. Saved preferences remain; controls become ready with zero activity. The button resets this app's session and does not switch the Windows radio off/on. Pending connection operations offer **Cancel**, and errors stay visible during background updates. Recovery still needs physical verification.

## Settings

Settings text/number fields have no outline; number fields have no visible up/down spinner arrows. Plain number fields repaint their full background, including the margins around the text, so old glyph fragments cannot remain after moving/resizing. Click and type to edit, with the existing numeric validation and keyboard support. The mouse wheel scrolls the surrounding page without changing number fields or dropdown selections, including toy limits and SPS connection options. Default OSC ports remain **9001 Listen** and **9000 Send**.

Enter the generated API token value in Settings. **Copy ID** on the API Tokens page copies the token's identifier, which cannot authenticate the bridge. Leave **Remember token on this PC** checked and select **Save settings**. Windows encrypts the token for your Windows account in `%LOCALAPPDATA%\SzebsToys\api-token.bin`; subsequent launches load it automatically and show masked dots. Uncheck Remember token and save to delete the encrypted copy. The current session continues to work. The bridge receives the token through `OPENSHOCK_TOKEN`; the JSON configuration contains no token. Other settings are saved as `SzebsToys\bridge-config.json` in the same application data folder. **Debug** contains Test mode. Connection retry delay and OSC ports remain shared settings.

The API status identifies missing setup as **Token needed** or **UUID needed**. Put the shocker UUID under **Options** on its card and select **Save options**; the bridge checks the connection immediately. A rejected token or inaccessible shocker is reported separately in the status and log.

With several shockers, the API card combines their connection states: **Connected (2)** means both UUIDs are verified and live logs are connected, while **1/2 connected** means one needs attention. Each shocker card shows its own API state; hover over that state for the error reason. Hover over the main API status for all shocker details, or click it to open **Log** and reveal the latest error. The bridge verifies each UUID, then receives live log events through one persistent connection. A debounced metadata read after connection/reconnection and relevant live change notifications keeps names current; there is no repeating name or history poll. It reconnects with increasing delays after interruptions. Failed UUID checks wait at least one minute between retries; HTTP 429 respects the server's retry delay. Device commands are never automatically retried. Slider adjustments never request history or activate a device; bottom maximums can update existing share settings as described below.

API failures appear as highlighted **ERROR** rows, with long messages wrapped. **Copy log** copies recent activity, including entries hidden by scrolling or cleared from the view. A rotating activity log is also kept at `%LOCALAPPDATA%\SzebsToys\activity.log`. API token values and configured shocker UUIDs are redacted before copying or writing log entries.

### Test your own devices from VRChat

Under **Settings → Debug**, enable **Control my own devices from VRChat** and check your own devices under **My test devices**. Add their cards and UUIDs on **Toy panel** first. **VRChat test group** defaults to `PiCtrl`; use the parameter group your avatar actually sends. Select **Save settings**.

While self test is enabled, that group's Intensity, Duration, and Action values go only to the checked devices through OpenShock, replacing the usual avatar group assignments for OSC actions. Several checked devices receive the same action, each clipped to its saved top/button range and respecting its own pause and cooldown. Manual card buttons continue to target their own card. API logs still return as avatar feedback and are never resent as device commands.

**Test mode** is independent: leave it checked to log the self test without activating a device, or turn it off to send real commands. The activity banner identifies self test and whether commands are enabled. Switching the test route discards pending OSC actions and waits for a fresh Action=0 before accepting another button press. Removing the last selected test device disables self test. Self test starts disabled for existing settings.

## Shocker cards

Use **Add shocker** on **Toy panel** for one card per shocker. Shocker cards retain their three-column grid and are 182 pixels tall when collapsed, twice the status panels' height. Additional rows and expanded options scroll with that page; logs have their own **Log** page.

Edit the name and model directly on the card. **Names sync both ways with OpenShock** while the bridge is connected: connecting loads the OpenShock name, and live change notifications refresh it after a rename in the other app. Edit a panel name and click elsewhere (or Save options) to save it to OpenShock. Renaming requires ownership and **Shockers Edit** token permission. Names contain 1–64 characters. Offline edits are saved as pending and sync on the next live bridge start; incoming names do not overwrite a pending local edit or a name field being edited. Test mode allows reading names but blocks outgoing rename writes. Failures appear under Options and in the log; Save options retries, or start a new bridge session. No repeating name/history poll runs. The model text on the card remains a local label; actual model/RF pairing data is read freshly from OpenShock and carried through its edit endpoint when renaming.

The top duration and intensity sliders are **your own button ranges**. They save automatically and restore on reopening, independently for each card. Pending slider changes also flush before a button command, settings save, or normal app close. The thick tracks and 30–32 pixel interaction areas remain. **Shock**, **Vibrate**, and **Sound** use the displayed upper values; their white text and brighter backgrounds remain readable while unavailable. Test mode logs those actions without sending them to a device.

Check **Options** (shown as **More** at narrow sizes) to edit the UUID, copy it, pause that shocker in this overlay, and set its cooldown. UUID and cooldown have the same brighter field background as Settings, without outlines or cooldown spinner arrows. Name/model fields keep their existing panel background and positions. The Avatar group field is removed; existing saved groups and custom OSC addresses are retained when saving options. At the bottom, **Limits for others** has matching duration/intensity sliders. The right handle sets the maximum; the left sets the minimum for commands routed through this app. Normal avatar control uses these limits; your manual buttons and explicit self-test use the top ranges. Values are clipped: 80 with a maximum of 40 becomes 40. Zero input remains ignored. Arrow keys make precise slider adjustments. Use **Save options** to apply the fields; sliders, pause, and name/model edits save automatically. Pause blocks new commands from this app; an already sent command may finish. Remove deletes the card and its local assignment, leaving the shocker in your OpenShock account.

Changing a bottom maximum saves locally and **automatically applies to OpenShock** after releasing the slider and pausing for 650 ms. Quick duration/intensity edits are combined into one update per card. Keyboard changes use the same delay. Holding a drag never starts an update. The top sliders and bottom minimum handles only save locally. Requires a running live bridge, ownership of the shocker, and an API token with **Shockers Edit** and **Publicshares Edit**. Test mode blocks OpenShock writes. Edits made while stopped, in test mode, or without a UUID report that they saved locally; they are not replayed on startup or reconnect. Stopping the bridge, removing a card, or closing the app cancels its queued update.

**Apply to OpenShock** remains available to retry a failed update or include newly added shares. The operation applies the lower sliders' maximums to existing OpenShock user shares and active share links, preserving tighter existing caps, command permissions, and pause states. Public links also receive this card's cooldown: zero means no cooldown, otherwise at least 0.3 seconds. Existing public-link cooldown is not returned by OpenShock's API, so this operation explicitly replaces it with the displayed card value. Its result is shown separately from local saving; permission, network and partial-update failures do not claim success. No device command is sent. A failed update is never automatically retried. If you change a maximum again while an earlier update is running, only your latest saved edits request one new update after the earlier operation finishes; this is a new user edit, not a retry of the failed settings.

These are caps for existing shares, not a universal limit on the OpenShock account. Reapply after adding shares. Unclaimed share codes, newly created shares, and people using your owner credentials are not covered. OpenShock supports share maximums only; lower-handle minimums apply to app-routed commands. Future ShockWave remote sessions still need their own authenticated receiver gate; the new Lovense/remote transport is not implemented here.

The first avatar group is `PiCtrl`; further cards default to `PiCtrl_2`, `PiCtrl_3`, and so on. A group uses `/avatar/parameters/<group>_Intensity`, `_Duration`, and `_Action`, with separate `_FeedbackEvent`, `_FeedbackActive`, `_FeedbackIntensity`, and `_FeedbackMode` outputs. Avatar Action values are 0 idle, 1 Shock, 2 Vibrate, 3 Sound. Your avatar must contain and send the matching parameters. The existing Unity generator creates the first PiCtrl group with Shock and Vibrate; adding a card alone does not add controls to the avatar. Assigning the same group to two cards sends its actions to both.

Existing single-shocker settings migrate into the first card, preserving the UUID, limits, cooldown, duration mapping, and OSC addresses. Existing cards seed the new saved manual ranges from their old ranges, retaining previous values in both sets. New groups map an avatar duration of 100 to 15 seconds before clipping it to the applicable range.

Test mode logs commands without activating the device. Turning it off requires a token, and the app asks for confirmation. Each shocker needs a valid UUID before it can send live commands. The bridge enforces the applicable range, pause, and cooldown for every manual or avatar command. Use the [bridge setup guide](../bridge/README.md) for the VRChat parameter setup and PC-only simulation.

## Build

Run `overlay/build.ps1` from PowerShell. It installs the locked bridge dependencies if missing, publishes the WinForms EXE, and copies the local Node.js runtime and live log client into `overlay/dist`. It then checks the actual EXE's hidden worker startup three times in an isolated folder without a native DLL; those checks cannot connect or activate a toy. An optional `-OutputDirectory` selects a different build folder. The live OpenShock and VRChat path still needs an end-to-end test with your own account and avatar; do not share your API token in chat.

### Hub connection status

**OpenShock Hub** uses the live `DeviceStatus` events on the existing OpenShock connection. No extra hub polling is started. Shocker metadata identifies each card's hub; several shockers on one hub count as one. A single hub shows **Online** (green) or **Offline** (red). Several hubs show **Online (2)**, **Offline (2)**, or **1/2 online** (amber). Hover over the status for the hub state associated with each shocker; the question mark explains powering the hub and Wi-Fi setup. State changes appear in the activity log.

An API connection can remain green while a hub is offline. **Checking** means the initial live snapshot or shocker-to-hub mapping is pending; **Unknown** means live status is unavailable. Losing the live connection clears previous online state, and reconnect waits for a fresh snapshot. Stopping the bridge clears the panel. Online confirms the hub's OpenShock connection only; it cannot confirm shocker battery, power, pairing or RF reception.
