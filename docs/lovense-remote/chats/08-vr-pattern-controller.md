## Selected approach and alternatives

1. **Avatar prop (selected first):** an avatar-installed panel dropped with a VRC Parent Constraint / Freeze To World. Avatar contact receivers can drive parameters exported over OSC. Local display/input filtering must be configured explicitly. This meets actual in-world placement and can supply touch intensity, buttons, destination choice and pattern selection. A complete editable scrolling graph needs a separate feasibility prototype for contact coordinate measurement, shader/animation rendering and OSC feedback; it is not a normal scripted app canvas. Do not promise an exact app replica before this prototype.
2. **Private SteamVR overlay (optional later alternative):** a dedicated controller surface rendered by the app or a bundled helper alongside VRChat. Supports a full timeline, controller-pointer drawing, editable curves, recording, presets, looping and save/load without avatar changes. Panel placement and dragging must be implemented. SteamVR absolute transforms are tracking/playspace coordinates, not automatically VRChat world coordinates; walking/teleporting in VRChat does not make this a prop anchored to an in-world table. Other VRChat players cannot see or touch this private overlay. The current WinForms folder name `overlay/` does not mean it already implements SteamVR overlays.
3. **World/Udon panel:** a rich world UI can implement curve editing, but must be installed by the world author. It cannot be dropped into arbitrary existing worlds. The documented avatar OSC path is not a generic Udon-to-UDP API; a separately verified world-to-app bridge would be required.
4. **Combined approach (optional later):** keep one app-owned curve engine and routing model, expose controls through the selected avatar prefab and optionally add a SteamVR editor later. An overlay is not a dependency of the avatar implementation.

- Chat 03/04: verified Windows WebRTC runtime, free entitlement/quota behavior and authenticated receiver grants. Remote targets may be modeled/mock-previewed before transport exists, but must report unavailable rather than pretending to control a peer.
- Local hardware: the existing default 5 normal writes/sec per toy, adjustable 1-10 and shared 20/sec ceiling, are application test ceilings. Multiple functions share their toy's allowance. UI drawing/render rates must remain separate from Bluetooth command rates; keep only current intent and avoid queued waveform replay.
- One active input controller per capability initially. Multiple destinations are allowed; silently mixing competing local, OSC and remote inputs is not.
- Route changes stop removed targets and invalidate pending intent; require fresh touch/Play before a new destination starts. Do not silently substitute Own for unavailable Remote.
- Stop cancels live input and pattern playback, clears pending output and invalidates old intent. Remote Stop is best effort over transport, backed by receiver freshness/watchdog rules. Reconnect never resumes old output.
- VRChat exports parameter changes, not a guaranteed periodic stream. Define and test separate source liveness/heartbeat behavior so holding a constant level does not falsely expire and source loss does not hold output forever. Avatar change, contact release, bridge/overlay/helper failure and remote disconnect need explicit behavior.
- Preserve configuration migration, saved limits, test mode and token storage. Save patterns/preferences only, never current actuator activity or authorization.

## Verification before calling this shipped

1. Simulated/test-mode curve drawing, record/play/loop/stop and bounded persistence; no physical output.
2. Destination/function selection, independent owner caps, route switch invalidation, competing-source arbitration, invalid/stale input, static-value liveness, helper/bridge failure and reconnect with no replay.
3. Avatar-first: uploaded-avatar contact/OSC output, calibrated intensity, constant-touch liveness, local visibility/self filtering, drop/recall through locomotion, avatar/world transitions and graph feasibility. Unity editor preview alone is insufficient.
4. Optional SteamVR overlay later: pointer/drawing/placement tests while VRChat is running, including locomotion/teleport expectations. Record actual runtime evidence separately from mock UI checks.
5. Remote option only: authenticated two-client behavior, stop/revoke/freshness and network faults, first with simulated toys. Physical latency, function support and stopping remain separate model-specific evidence.
