## Using the app

**Forget toy** works only on a remembered offline toy. It stays disabled while connected, connecting or disconnecting; the adapter also rejects a queued request if the toy connects before it runs. Turn the toy off and wait for Offline first. Forget deletes its saved entry and removes every function card, including offline entries retained by the bundled engine. The session exclusion also blocks late engine notifications from remembering it again. Connected toys retain their saved identity. The disabled Forget background is darker; enabled and disabled toy-option button labels use the app's white text.

The closing warning appears for any connected physical local toy, including idle/zero Input and Test mode. It says the toy is still connected. Offline/forgotten history and simulated toys alone do not keep the warning active; bounded OpenShock activity remains independent. This is connection state, not measured physical stop confirmation.

For the bundled engine, automatic first/five-minute battery reads run independently of the coordinator's missing-toy search. The adapter still serializes individual management requests; discovery and existing output stay available. Legacy battery reads retain their existing serialized path and defer while scanning. Unknown/failed readings keep the five-minute interval without rapid retries.

Open **Toy panel** for the Bluetooth toy cards. Each supported function has its own 182-pixel card in a three-column grid, matching shocker spacing. Name/function are top-left, Max % and Stop top-right, and Input/Sensitivity sliders at the bottom. Options/More expands to show battery, Read battery, Forget toy and Stop toy; function Stop affects only its function, while Stop toy clears every sibling. Unknown functions remain visible with unavailable controls. The separate Local toys tab is removed.

Choose the source under **Settings → Bluetooth toys**: **Simulated toys** discovers/connects automatically without hardware. Four simulated devices cover two/three vibration motors, vibration plus rotation, and unknown functions. Duplicate advertisements are deliberately emitted. Simulated discovery takes 0.6 seconds. Connected toys remain present even if they stop advertising. **Simulated Bluetooth off** exercises unavailable setup. Source/reset/cancel/all-toy Stop and Updates/toy/sec are in Settings.

The second status row shows Bluetooth, Ingame curve, Scan toys and Reset Bluetooth. Bluetooth reports adapter readiness, explicitly distinguishing simulation. Ingame curve is Inactive until later production integration. The scan panel is clickable: Scanning stops discovery, and Inactive starts it. Explicit stop pauses background discovery until another manual scan/reset; scans otherwise finish automatically. The eighth panel replaces the connected count and runs the existing reset: stop app-owned toy activity, release sessions and reconnect with zero Input and retained sensitivity/maximums. Busy prevents overlapping operations. Local errors appear in Log.

Choose **Lovense Bluetooth**, enable Windows Bluetooth and turn on the toys. Startup discovers/connects remembered and new toys automatically. Once an eligible toy advertises, automatic scanning collects additional toys for 250 ms without a new candidate, capped at 750 ms from the first candidate, then stops and connects the found toys. Offline remembered toys do not delay that batch. Duplicate advertisements do not extend collection. These are application wait bounds after discovery, not radio/SDK/connection deadlines. **Scan toys** remains an explicit full scan (up to 15 seconds); new toys connect when it finishes or is stopped. Connect/Disconnect/Auto-connect controls are removed. OpenShock credentials/bridge startup are independent.

Battery is read once after each confirmed connection, then every five minutes while connected. Each physical toy has one schedule and one shared reading across its function cards; identical toys keep independent schedules. Reads wait until scanning finishes and use the existing serialized battery request without changing Input or Stop. **Read battery** remains available for an immediate manual refresh, which restarts that toy's five-minute interval. Unknown replies, timeouts and failed requests wait until the next interval; a reconnect starts a fresh read. Battery remains unknown until a valid response arrives, and 0% is valid. Disconnect/Bluetooth loss/reset clears the reading and schedule; battery is never saved with remembered toys.

Confirmed connections are remembered. The page enables automatic-all mode regardless of old saved Auto-connect flags; successful saves mark connected entries enabled without a schema migration. Discovery matches installation keys to fresh native IDs, stops scanning, then connects toys individually. Loss starts recovery at the next tick (about 100 ms), but scans wait while any local function is active because scan preparation stops output. Missing/failed toys and empty discovery retry after three seconds; legacy internal flag mode keeps its old delay. Native TOY_NO_CONNECT clears stale connection/battery state. User-started scans remain running until completion/Stop scan, then fresh candidates connect without a redundant scan.

After an early automatic batch, startup discovery can continue after a one-second gap to find later advertisements. All-new collection uses the remaining 15-second startup scan budget and ends early when all toys saved at startup have been found. Once a toy is connected, the first follow-up search yields after two seconds. If a known eligible toy is still missing and no candidate appeared, subsequent searches allow an uninterrupted full scan (up to 15 seconds), even if the startup budget is nearly exhausted. A found candidate still connects after the short advertisement batch; healthy toys are not disconnected/reset for this longer search. Follow-ups require idle output and obey explicit Scan pause/cancellation. Fresh manual discoveries connect before any search for absent saved toys can clear them. Fully connected inventory after startup triggers no periodic scans. These are software coordination bounds; native/radio timing and physical recovery remain unverified.

Remembered **Offline** cards retain accessible options during recovery. **Cancel operation** in Settings aborts a pending operation/connection attempt. Canceling an automatic connection also pauses background discovery until a new scan/reset. Native cleanup can still wait for bounded acknowledgements. Errors remain visible in Log and Bluetooth status details. Connection, readiness and preference edits while idle never submit positive output.

Lost native sessions are released before scanning. The DLL runs in a hidden child process. Loss/disconnect/failure marks it for replacement before the next scan when no other toy is connected. Replacement clears native state/private IDs and requires fresh discovery. **Reset Bluetooth** releases all toys, replaces the process and discovers/connects automatically. Preferences remain; controls become ready with zero activity. It resets the app's session, not Windows Bluetooth. The user confirmed corrected worker startup; repeated physical recovery remains unverified. Native connection errors clear on confirmed recovery; manual errors persist until another operation/reset.

Identical models have separate rows/keys, distinguished by suffixes; matching never uses model name alone. Remembered toys load Offline with unknown battery until rediscovered. Old native IDs are never saved/reused across sessions. **Forget toy** is available only offline: it deletes its saved entry and excludes reconnection for this session; reopen/Reset Bluetooth to rediscover it. Turn the toy off and wait for Offline first. Simulation is memory-only; function settings survive source/reset within the page session. Legacy individual-flag/manual-disconnect APIs remain internally compatible without page controls.

An interrupted scan preserves earlier inventory. A completed scan marks previously discovered, unconnected toys that were not seen as unavailable. Connected toys may stop advertising and remain connected until a disconnect/Bluetooth-loss callback or adapter cleanup. This is scan-based presence, not proof of continuous proximity.

## Native dependency setup

The wrapper targets the official **Lovense Windows BLE DLL v1.2**, Windows 10+ x64 and a usable Bluetooth adapter. No standalone Lovense Remote or Intiface app is needed.

This is the **Windows Bluetooth / BLE** path, not the separate Lovense dongle SDK. A built-in radio or a USB Bluetooth adapter can be used if it supports Bluetooth Low Energy through compatible Windows drivers. The official Lovense dongle is not required, and compatibility with every older Bluetooth adapter or driver is not guaranteed.

The vendor DLL is **not included or downloaded by the app/build**. Its redistribution entitlement has not been established. Obtain it from the [official BLE library page](https://developer.lovense.com/docs/game-engine-plugins/windows_ble) subject to the applicable vendor terms. For a local installation, place `LovenseBLE_Lib.dll` under `native/lovense/` beside `ShockWave.exe`, with any required native dependencies. For a source build, that same directory under `overlay/` is copied during build/publish. Vendor DLLs are ignored by Git.

Only that absolute application-relative path is loaded; the wrapper does not search the current directory or PATH. Missing library, wrong architecture/exports, disabled Bluetooth, missing Bluetooth, and callback timeouts receive visible status. An unconfirmed scan stop resets the adapter's Bluetooth resources before further requests.

For this local checkout, the official DLL was installed into both `overlay/native/lovense` and `overlay/dist/native/lovense` on 2026-10-08 after the user reported the missing-library status. Windows load and all 12 required export lookups passed in a separate process, without invoking Bluetooth or toy functions. The file is ignored by Git. The user subsequently reported a successful connection; battery, multiple-device and reconnect behavior still need physical verification.

The classic [Windows SDK](https://developer.lovense.com/docs/native-sdks/windows-native-sdk) requires a developer token. The selected BLE DLL's documented exports and supplied C# demo contain no developer-token initialization parameter. No token is added for this wrapper; any additional vendor account/licensing requirement remains to be confirmed. Do not infer redistribution permission from download availability. The [vendor EULA](https://www.lovense.com/end-user-license-agreement) includes developer materials in section 12.

## Implemented local descriptor contract v1

Source: `overlay/Toys/LocalToyModels.cs`; adapter: `LovenseDiscoveryAdapter`; UI: `LocalToysPage`.

| Field | Meaning |
| --- | --- |
| `DescriptorVersion` | 1; local inventory schema, separate from the draft network version |
| `DeviceKey` | Installation-scoped HMAC key; never use as a remote channel alias |
| `Adapter` | `lovense-ble` or `simulated-lovense` |
| `DisplayName`, `Model` | Catalog label, with a family label where symbols cannot identify a revision |
| `ConnectionState` | Discovered / Connecting / Connected / Disconnecting / Disconnected / Unavailable |
| `CapabilitiesKnown` | False for unknown model symbols; an empty list is not a guessed vibrator |
| `Capabilities` | Independent channel descriptors with `ChannelId`, type, label, nullable native range/step, nullable stop/status support |
| `BatteryPercent` | Nullable integer 0–100; cleared on disconnect, Bluetooth loss, or resource reset |
| `LastSeenUtc` | Time of the latest discovery callback; local inventory metadata, never a remote freshness clock |
| `ConservativeCommandsPerSecond` | Local adapter ceiling, not measured hardware capacity. The page creates adapters with a 10/sec ceiling; its controller defaults to a 5/sec target, adjustable 1–10 for the session. Functions share their toy's allowance and all toys share a 20/sec normal-output ceiling. Standalone adapter callers retain the default 5/sec ceiling. |
| `IsSimulated` | Explicit simulated evidence marker |
| `IsRemembered`, `AutoConnect` | Additive local v1 fields: confirmed connection saved, and its individual reconnect preference |
| `AutoConnectPaused` | Session-only pause after manual disconnect; never an output permission |

The public inventory contains no raw vendor IDs, Bluetooth addresses, or advertised names. IDs stay in the adapter's memory and are used only for native calls. A random 32-byte installation salt is stored as `%LOCALAPPDATA%/SzebsToys/local-toy-key.bin`; it contains no hardware identifiers. Keys prefer normalized Bluetooth addresses, falling back to the vendor ID. Stability across address/ID rotation is not guaranteed. Deleting the salt changes all keys. Simulation uses a separate deterministic namespace.

`RememberedToyAdapter` wraps the discovery adapter through `IRememberedToyAdapter` (initialize, set per-toy auto-connect, forget). `RememberedToyStore` saves version 1 data in `%LOCALAPPDATA%/SzebsToys/remembered-toys.bin`, encrypted with Windows DPAPI for the current user. Only opaque installation keys, catalog model labels, the auto-connect flag and last-seen metadata are saved. No raw native IDs/addresses, advertised names, connection state, battery, actuator command, or remote permission is persisted. Writes replace the file via a temporary sibling. Invalid/unreadable saved data is kept and blocks new saved changes; manual discovery/connection remains available with a visible warning. No existing OpenShock configuration or token migration changes. A missing remembered file is a normal first run; reconnect each toy once in the updated app to create its saved entry.

`v1`, `v2`, and `v3` identify independent vibration motors. Aggregate `v` is omitted when independent motors are present, preventing an overlapping master channel from being mistaken for another motor. Non-vibration functions have their own types; position, depth, and thrusting are not all intensity. Stop/status support remains null until verified. Chat 02 fills documented scalar ranges with step 1: most speeds 0–20, pump/depth 0–3, position 0–100. Physical stop/status support remains nullable.

Model facts were normalized from the official support CSV fetched on 2026-10-07 (actual file version 1.6; page still mentions 1.5). Repeated symbols in that file make some revisions ambiguous. The catalog uses family names and the common functions of those revisions, rather than trusting the first/last duplicate row. It does not infer extra functions from advertised names or marketing descriptions. Model/firmware confirmation belongs to 02 before enabling physical output.

## Ownership, callbacks, and cleanup

The WinForms process owns the adapter, inventory, persistence and `LocalToyController`. `LovenseWorkerApi` starts a hidden copy of the same EXE with `--lovense-worker`, using private UTF-8 JSON-line pipes. `LovenseWorkerHost` alone loads the DLL and serializes native calls. UI updates marshal back to the UI thread. Native callbacks cross the private pipe into inventory under a separate lock; callback failures cannot unwind through unmanaged code. No toy descriptors or commands are sent through the existing OpenShock bridge. Simulation needs no child process.

UTF-8 is configured on the pipe readers/writers directly. Setting Console.InputEncoding crashed the first process-isolated published build because the hidden WinExe has no console handle; that packaging-specific fault was reproduced and corrected. Startup messages now distinguish a Windows launch error, an early process exit (with code) and a timeout, instead of only suggesting Reset Bluetooth.

The native binding follows the official **C# demo**: discovery has five callback arguments (ID, name, address, two model bytes), and notifications have an integer plus ID. The documentation's C++ sample uses different signatures; it was not used as the ABI contract. This discrepancy remains a physical/runtime verification item. Calling conventions are equivalent on the selected Windows x64 target; other architectures are rejected.

Stop cancels the scan deadline and ignores discovery after a stopped scan. Connect/disconnect operations wait for status callbacks; receipt of a request is not reported as a connection. Battery requests can only invoke `_SendCommand(id, 12, 0)` (`GET_BATTERY`); the discovery interface remains separate from the local scalar output transport. Chat 02 routes every manual output through the owner controller; EventsAPI telemetry is not implemented. Test mode blocks both OpenShock and the new local actuator path; zeros that stop prior live activity remain allowed.

On source switch or app close, operations are canceled, scanning stops, callbacks unsubscribe, owned output is stopped and `_Quit` releases Bluetooth resources. Cleanup is idempotent. Because `_Quit`'s callback drain/unload guarantee is undocumented, DLL/callback roots remain resident only until that child exits. Each replacement gets fresh process state, instead of retaining native wrappers in the main app.

The parent sends a heartbeat every 250 ms. Pipe closure or 1.5 seconds without heartbeat rejects further positive commands, attempts zero/disposal and exits; the child bounds cleanup at 700 ms. The parent bounds ordinary native-call acknowledgements at five seconds and forces a worker exit after one second of stalled normal shutdown. Unexpected worker loss invalidates connections/battery and closes the main output gate. An acknowledgement means DLL-call return, not physical execution. No output is restored or replayed after recovery. A blocked DLL/device or PC failure can still defeat physical zero; process termination alone cannot guarantee the toy stops. The private contract is recorded in [PROTOCOL.md](PROTOCOL.md).

## Function settings and readiness (chat 02)

Each function has separate Input and Sensitivity dot sliders (0–100%), Max %, status and Stop. Moving Input supplies a local request: 0 is off, 100 requests full power within Sensitivity/Max %, and the latest value stays active until changed/stopped/disconnected. Enable controls/Seconds/Run remain removed. Healthy connected functions become ready with zero input. OSC/SPS/remote input is not implemented by this change. Idle Sensitivity/Max edits cannot start activity. Sensitivity/Max defaults remain 100%. Preferences stay per opaque key/channel in `local-toy-controls.json` v1; legacy duration is parsed/preserved without applying to this page mode. Invalid control files are kept, block overwrites and automatic readiness. Input/activity/deadlines are never saved/restored.

Effective level is `min(input × sensitivity / 100, maximum)`, rounded down to a native step. Zero always stops. **Sent** reports the last native value whose submission call returned successfully as a percentage; it does not advance while waiting for transport access and is not measured motor speed or physical confirmation. Test mode displays **Preview** without invoking actuator commands. Native execution notifications lack channel/request IDs, so failures pause the entire toy and no success is guessed from unrelated acknowledgements. Per-motor EventsAPI telemetry is not implemented.

`LocalToyController` owns the gate. The page uses `automaticControls=true`, holding local input until replaced/zeroed/stopped/disconnected instead of applying a countdown. Stop, explicit scanning, disconnect, source switch, test transitions, native errors and shutdown discard activity/revisions. After successful zero, healthy controls become ready and only fresh input can restart them. Native output/zero failure stays closed until recovery; raising a zero preference cannot revive old input. Internal default bounded manual mode retains 0.25–15-second monotonic expiry for compatibility/regressions. Future remote grants/source generations/disconnect revocation/live watchdogs remain separate routing prerequisites; local readiness is no remote authorization. No retry/reconnect replay occurs.

One shared scheduler retains one replaceable value per function, suppresses unchanged native steps, serves the least recently served eligible toy and then its least recently sent function. **Updates/toy/sec** defaults to 5, accepts 1–10, and is shared by all motors/functions of each toy. The normal-output ceiling across toys is 20/sec. Both are unmeasured test ceilings, not Bluetooth capacity guarantees. The pace choice survives source/reset within this page session and resets to 5 when the app is reopened; it is not saved with control preferences. Changed input wakes the scheduler immediately, with a 10-ms idle watchdog check. Each pass attempts at most one normal write, then revisits expiry and all zero requests.

Ready different toys now submit in groups of at most four, with one normal write per toy in the group. Calls remain serial through the existing worker; no concurrent vendor calls are introduced. Every successful write reserves 50 ms of shared allowance from submission time, and the next group waits for the resulting allowance. A bounded rolling window also limits successful ordinary submissions to 20 in one second. Idle time earns no credits, per-toy intervals and fair turns remain, and unchanged/canceled values consume no allowance. Unchanged native steps are checked again during selection to cover requests arriving after the preliminary scan.

`ILocalToyOutput.TrySendLevel` and the BLE proxy pass a parent-memory freshness guard through the remembered adapter, discovery output lock, serialized worker-call gate and pipe-write gate. The guard rechecks current revision, arming/test/stop state and original monotonic expiry immediately before submission. Replaced or expired input is dropped without retry or consuming a normal-output slot. An already submitted native call cannot be revoked. Stop bypasses the ordinary pacing allowance, and rearming is blocked until its zero submission returns. Controller/inventory locks are released before native writes, keeping slider/state/Stop interactions responsive during a slow write or callbacks. A blocked in-flight native call can still delay zero; no hard physical stop deadline is claimed.

Settings diagnostics report pending/submitting function counts and the per-toy target. Function-state tooltips and diagnostics show **wait** (latest input to final submission guard) and **submit** (guard to successful pipe/DLL-call return), in milliseconds. Time spent inside a slow successful call now counts toward pacing instead of adding another shared pause afterward. A completed zero likewise adds no extra shared pause to unrelated ready toys; previously reserved ordinary allowance remains. A blocked native call still prevents later calls from entering the serialized library. These measurements do not observe radio completion, per-motor execution or a hidden vendor/device queue. Physical calibration with one function, a multi-function toy and four toys remains required; a delayed physical response with short wait/submit times would motivate investigating the backend.

Native command IDs follow the official BLE C# example: `v/v1/v2/v3 = 0/1/2/3`, `r/p/t/f/s/d/pos/o = 4/5/6/7/8/9/10/11`. Native ranges are documented as 0–20 for vibration, rotation, thrusting, fingering, suction and oscillation; pump/depth 0–3; position 0–100. Command IDs come from the BLE page/example, with scalar ranges/depth/position semantics cross-checked against the Windows Unity and standard API references. These software facts are not hardware verification for every model/revision. SupportsStop/SupportsStatus remain null; unknown/ambiguous extra functions remain unavailable.

Depth is a setting for thrusting. Position moves to a point, not a stroke-range slider. Zero on either sends thrusting zero instead of moving to endpoint zero or changing depth to its zero setting. Stop/expiry clears related pending thrusting, depth and position together. These typed semantics are local controls, not a remote intensity contract. Rotation direction, device patterns and Solace Pro stroke-range controls are not exposed here.

Local controls require neither bridge startup nor an OpenShock token. Settings save validates without requiring that backend's credentials; both validators require a token for configured live OpenShock UUIDs. The form forwards shared Test mode on startup and saved changes. Existing OpenShock migration, token storage, limits and no-retry/no-replay remain supported.

Post-await layout/source-switch changes explicitly run on the owning UI thread. Fixture diagnostics exposed a worker-thread DataGridView update that could stall source switching; the offscreen tests now exercise its correction. Native failure events dispatch away from the callback reader to avoid an adapter/controller lock inversion. The private BLE child process does not change the OpenShock bridge or add a remote session.
