## Lovense

Chat 01 rechecked the official Windows SDK/BLE pages on 2026-10-07, inspected the linked C# demo and support CSV, and inspected the downloaded BLE DLL's PE architecture without executing it. The selected BLE v1.2 wrapper follows the C# demo's five-argument discovery and integer/ID notification callbacks; the page's C++ example differs. The support CSV currently reports 1.6, while the page text still says 1.5. Duplicate symbols mean some revisions cannot be uniquely identified. Native compatibility, redistribution entitlement and physical behavior are not established by this inspection. See [LOCAL-TOYS.md](LOCAL-TOYS.md).

The classic Windows SDK documents a required developer token; the BLE DLL's documented exports and C# demo have no token initialization parameter. This is an interface observation, not a licensing conclusion. The [vendor EULA](https://www.lovense.com/end-user-license-agreement) explicitly includes developer materials in section 12; no confirmed redistribution permission was found in the inspected package/page, so the vendor binary remains locally supplied and unbundled.

- [Standard solutions](https://developer.lovense.com/docs/standard-solutions): requires Lovense Remote for toy pairing. This does not meet the standalone Szebs-on-both-ends goal.
- [Native SDK overview](https://developer.lovense.com/docs/native-sdks): native app integrations.
- [Windows SDK](https://developer.lovense.com/docs/native-sdks/windows-native-sdk): direct toy access; developer token setup; older SDK guidance recommends no more than one command/second.
- [Windows BLE library](https://developer.lovense.com/docs/game-engine-plugins/windows_ble): native scanning, connection, commands, battery, and device events. No guaranteed high-frequency command rate was established.
- [Standard Socket API](https://developer.lovense.com/docs/standard-solutions/socket-api): official internet control through Lovense Remote; an alternative if the user later accepts the extra app.

- [Metered free signalling offer](https://www.metered.ca/tools/openrelay/webrtc-signaling-server/): advertises 100 concurrent connections, 100,000 monthly messages, no credit card, and Open Relay integration.
- [Open Relay offer](https://www.metered.ca/tools/openrelay/): advertises 20 GB/month.

- [Messaging limits](https://www.metered.ca/docs/realtime-messaging/limits-and-quotas/): free hard caps; blocked outbound sends at exhaustion; 100 sustained service messages/second per connection. This is not the P2P data-channel frame limit.
- [SDK getting started](https://www.metered.ca/docs/realtime-messaging/sdk-javascript/getting-started/): convenient send APIs are server-routed by default. Use a real RTCDataChannel for rapid values.
- [TURN regions](https://www.metered.ca/docs/turnserver-guides/turnserver-regions/): region/endpoint availability depends on plan; confirm actual free-account routing.
- [Terms](https://www.metered.ca/terms): free plans have no SLA/support obligation and can change/withdraw; relay metadata is retained; paid overage/top-up rules must not be assumed to apply identically to the free offer.

Do not claim the free TURN exhaustion behavior is verified until the account's actual entitlement and cutoff settings have been checked. The allowances are shared by the app account.

## Transport and alternatives

- [WebRTC data channels, RFC 8831](https://www.rfc-editor.org/rfc/rfc8831.html): ordered/unordered and reliable/partially reliable channels.
- [TURN, RFC 8656](https://www.rfc-editor.org/rfc/rfc8656.html): relay traversal and peer IP privacy tradeoffs.
- [WebSocket, RFC 6455](https://www.rfc-editor.org/rfc/rfc6455.html): persistent TCP-based connections.
- [Buttplug](https://github.com/buttplugio/buttplug): multi-brand adapter alternative, BSD 3-Clause; current engine lives in this repository. Bundling would still need runtime/packaging work.

## OSCGoesBrrr compatibility

**Detection comparison, 2026-10-12 (research, not shipped behavior):** inspected the public OSCGoesBrrr main commit `643aedd493ba21b0c0859ce6e57708fe408ee9c0`. Its [bridge grouping](https://github.com/OscToys/OscGoesBrrr/blob/643aedd493ba21b0c0859ce6e57708fe408ee9c0/src/main/bridge.ts) recognizes OGB, TPS_Internal and VFH/Zone families by type/ID, then clears transient game devices on avatar change. [OscConnection](https://github.com/OscToys/OscGoesBrrr/blob/643aedd493ba21b0c0859ce6e57708fe408ee9c0/src/main/OscConnection.ts) populates missing parameters from a bulk snapshot; [query discovery](https://github.com/OscToys/OscGoesBrrr/blob/643aedd493ba21b0c0859ce6e57708fe408ee9c0/src/main/services/VrchatOscqueryService.ts) checks mDNS and a log-derived loopback port. [GameDevice](https://github.com/OscToys/OscGoesBrrr/blob/643aedd493ba21b0c0859ce6e57708fe408ee9c0/src/main/GameDevice.ts) uses companion Close contacts for body touch, plug rubbing and legacy other-plug contact, with independent self/other length state.

ShockWave already reads bounded fresh OSCQuery snapshots and preserves full generated contact stems for distinct identities. Current recognition filters snapshots to its OGB/Pen, OGB/Orf and VFH/Zone/Touch allowlist; it does not support TPS_Internal, inventory unsupported zero-valued query contacts, or separate current-avatar presentation from the saved all-avatar board. Close companions are recognized but skipped by dynamic compilation rather than used as interaction gates. Proposed next work is a bounded discovery inventory/classifier, explicitly verified legacy/additional-family support, current-avatar/offline display without deleting saved layouts, clearer kind/ID labels and companion close gates. Read-only log-port fallback can help discovery failures; loosening TTL or routing arbitrary unknown floats is not a detection fix. These gaps do not establish which caused an individual friend's missing contact; an emitted address/current snapshot is needed for that diagnosis. VRChat exposes the local avatar's contacts, not an inventory of another player's private plug/socket names. No upstream code/artwork was copied and no parser, output, avatar, settings or transport behavior changed in the gear update.

**SPS current-value review, 2026-10-11:** [VRChat OSCQuery](https://docs.vrchat.com/docs/oscquery) and the [official current-values wiki](https://github.com/vrchat-community/osc/wiki/OSCQuery) support local readable snapshots while [avatar UDP output](https://docs.vrchat.com/docs/osc-avatar-parameters) emits changes. Read-only inspection observed a held mouth tip and positive root, explaining the expired-tip failure. Original `SpsOscQuery` uses [GetExtendedTcpTable owner-PID discovery](https://learn.microsoft.com/en-us/windows/win32/api/iphlpapi/nf-iphlpapi-getextendedtcptable), validated loopback HOST_INFO and bounded current-value GETs under the [OSCQuery JSON specification](https://github.com/Vidvox/OSCQueryProposal). Production discovery/readback succeeded separately from mock routing, without an output controller or settings writes. No library/license dependency was added.

**SPS depth review, 2026-10-11:** inspected official [SpsDepthContacts geometry](https://github.com/VRCFury/VRCFury/blob/main/com.vrcfury.vrcfury/Editor-Avatars/Builder/Haptics/SpsDepthContacts.cs) together with the [OGB socket contact builder](https://github.com/VRCFury/VRCFury/blob/main/com.vrcfury.vrcfury/Editor-Avatars/Service/BakeHapticSocketsService.cs) and [plug builder](https://github.com/VRCFury/VRCFury/blob/main/com.vrcfury.vrcfury/Editor-Avatars/Service/BakeHapticPlugsService.cs). Internal depth receivers use 3 m; OGB NewRoot/NewTip use 1 m. Original `SpsDepth` adapts approach length/root-distance geometry to OGB 1 m plus the 1 cm root contribution, with no invented default length. Pen/Touch/Frot contact tags determine other/self socket/plug/body filters. Synthetic insertion/movement checks pass; actual avatar orientation/scale/contact timing and multiple plugs are unverified. Earlier raw-proximity-only conclusions below describe the preceding tab. No OSCGoesBrrr source or artwork was copied.

## Chat 02 native control references (2026-10-08)

Rechecked the [Windows BLE DLL reference](https://developer.lovense.com/docs/game-engine-plugins/windows_ble), its linked official C# example and support CSV (still v1.6). Native `_SendCommand` IDs 0–11 correspond to scalar capability types; the existing battery command remains 12. The example/DLL exposes a void submission without per-command IDs; generic execute notifications cannot prove per-motor physical output. Vendor example artifacts were inspected under ignored `work/lovense-sdk-check`, not copied into production source.

Cross-checked function ranges and settings using the official [Windows Unity plugin](https://developer.lovense.com/docs/game-engine-plugins/unity-plugin-winbluetooth) and [standard API](https://developer.lovense.com/docs/standard-solutions/standard-api). Speeds 0–20, pump/depth 0–3 and position 0–100; depth requires thrusting, position moves to a point. The generic local rows do not implement stroke-range/patterns or rotation direction. These cross-interface documentation checks still need physical confirmation for the selected BLE DLL and actual models. The conservative one-command/sec rate follows the [Windows native SDK guidance](https://developer.lovense.com/docs/native-sdks/windows-native-sdk); it is not a measured BLE rate.

Follow-up on 2026-10-08: re-read the official BLE and Windows native SDK pages after user-reported slider latency. The native SDK still recommends one command/sec for best results; the selected BLE DLL page states no guaranteed rate. The implementation's new bounded five-write/sec target is an application tuning choice for physical testing, not vendor-confirmed throughput. The BLE page defines notification 9 as TOY_NO_CONNECT; it now invalidates stale local connection/battery state and permits enabled connection rediscovery, without actuator retry or replay.

Reconnect follow-up on 2026-10-08: the [BLE reference](https://developer.lovense.com/docs/game-engine-plugins/windows_ble) documents `_Quit` as releasing Bluetooth resources; it does not establish callback-drain/safe-unload guarantees or recovery from the user's repeated power-cycle failure. The user reports that same-process Reset Bluetooth/Forget failed while reopening the app restored connection. Process-scoped native state is an implementation inference from that report. The DLL now runs in a replaceable hidden child process; fixtures model native state that cleanup cannot recover. This change is not vendor-confirmed diagnosis or physical verification.
