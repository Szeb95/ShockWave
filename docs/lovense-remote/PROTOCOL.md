## Saved-friend extension to direct v1 — source only, 2026-10-22

This optional extension is not in published 0.7.6. Temporary `SW1.` invitations retain their 24-hour validity and RAM-only secret, but the updated app supplies its separately protected stable setup ID to the worker. Saving a friend does not extend or persist the invitation.

After the existing authenticated fingerprint/clock handshake, reliable `friend` envelopes use the existing three-second management freshness bound. Payloads are `{op:"hello",version:1,id,nonce}` (stable setup ID and fresh 32-byte hex nonce) and `{op:"save"|"saved"|"failed",request}` (fresh 16-byte hex request). Hello IDs must equal the authenticated signalling peer ID. Only one nonce per peer/connection is accepted. Both endpoints derive a per-friend 32-byte key as HMAC-SHA256 of the invitation secret over JSON `["ShockWave saved friend v1", [[id,nonce],[id,nonce]]]`, ordered by ordinal ID. The fresh nonces stay inside the encrypted channel; an old invitation alone cannot derive the durable key. Derived keys never enter signalling, application device messages or logs.

Either owner can select Save friend. The caller first writes its local encrypted entry, then sends `save`; the receiver writes its entry before sending `saved`. Storage acknowledgment is private native IPC, not peer-provided file access. Requests are bounded to two pending/four completed IDs and expire after ten seconds; duplicates do not allocate new entries. Simultaneous saves derive the same key. A failed/unconfirmed transaction is reported and may leave an unconfirmed local entry; it grants no output and can be forgotten/re-paired. Existing stored IDs cannot have their keys silently replaced. Once saved, both workers retire their temporary invitation and select the new saved target for subsequent retries. The active authenticated session is not restarted by Save and gains no output claim.

Private enable IPC additionally accepts `identity` and optional `friend:{id,secret}`; `remember-friend` initiates saving, `friend-stored:{request,ok}` acknowledges native storage. Session-bound `friend-ready`, `friend-save`, `friend-saved` and `friend-failed` worker events update the native book/UI. Save events/keys stay on the owned private pipe. Native storage format 1 is `{Version:1,Id,Friends:[{Id,Name,Secret}]}`, protected with Windows DPAPI CurrentUser under separate `ShockWave.RemoteFriends.v1` entropy. Display names are local, printable and at most 48 characters; no provider credential or hardware identifier is stored there.

Saved reconnect has no invitation expiry: both Connect switches must be on with the matching saved target. The lower ordinal setup ID initiates; the other accepts only the selected peer and its per-friend HMAC/fingerprint proof, avoiding simultaneous offers. Unknown peers/keys cannot fall back to invitation authentication in saved mode. Forget closes the local session/worker and removes the saved entry; the counterpart's retained key and retired invitation cannot restore it. Connect starts off after restart. New sessions, aliases, state/shock freshness, receiver gates and no replay remain as in v1 below. Older peers ignore the optional kind and retain temporary-code connections, with Save unavailable. No TURN, own server, provider protocol or Unity change is included.

## Implemented direct app protocol v1 — 2026-10-19

This section defines the implemented ShockWave connection path; the generic remote draft below remains historical/planned where it differs. The owner's current policy is that private-code pairing plus both **Connect** states on authorizes connected supported local functions automatically. There is no per-toy approval or reciprocal-operation requirement. Either owner can disconnect; existing receiver limits/Test mode/Stop remain authoritative. Automatic reconnection while enabled starts with fresh identities and zero activity. TURN is explicitly excluded from this implementation.

`bridge/remote-worker.mjs` uses PeerJS Cloud's public WebSocket signalling for SDP/ICE only, with standard data-connection metadata and an invitation HMAC in offer metadata. The receiving worker verifies the offer before creating a peer. Its own reusable, RAM-only `SW1.` invitation contains a random peer ID, 256-bit secret and fixed 24-hour expiry. The secret is not sent to the broker. Expiry is also enforced by the host; a new secret is generated after expiry. Process restart changes the code. Connection candidates use STUN plus local IPv4/IPv6 only; TURN configuration and relay candidates are rejected. The pinned Node runtime uses werift 0.25.1, not a presumed browser RTCPeerConnection.

`sw-control` is a reliable ordered encrypted data channel for authentication, clock probes, inventory, results, Stop and discrete shocker messages. `sw-state` is unordered with zero retransmissions. A separate HMAC challenge binds both actual SHA-256 DTLS fingerprints to the invitation secret. A SHA-256 session ID binds that pair and secret. Clock-offset/uncertainty estimation completes before application input is accepted; one bounded early inventory is retained during that handshake. RTT is connection telemetry, not physical feedback.

Local arbitration correction (0.7.2): automatic SPS cannot replace a live interactive input lease, including an interactive zero. After release it requires a later fresh contact, while explicit owner Input/Stop still requires neutral rearming. Receiver-local owner revision/time and last-source metadata distinguish these transitions even between SPS ticks; these fields are never sent to the peer or persisted. A newer remote claim can replace that same live session source without first ending it and queuing an unnecessary zero. Old claims, owner Stop, expiry, changed-controller cleanup and receiver caps retain their gates. There is no network wire-version change.

Application envelopes are `{version:1,session,kind,sequence,sentAt,payload}`. Sequence is a safe positive integer, tracked separately per message kind. `sentAt` originates at the UI snapshot, not after pipe/network waiting. From 0.7.3, continuous toy **state** expires at **500 ms** including estimated clock uncertainty; discrete **shock** retains **250 ms**, and inventory/management messages retain three seconds. Both the sending worker and receiving peer enforce the type-specific limit. The UI subtracts worker-to-UI age from that remaining lifetime and rejects a nonpositive remainder, without rounding expired data into a new lease. This explicitly replaces the overly tight 250 ms state limit; both apps should update. One newest incoming state replaces pending state; channel and IPC pressure are bounded. No queued state is timestamped fresh on release from congestion. A receiver with excessive delay cannot silently extend old activity.

- `inventory`: `{toys:[{id,name,battery,functions:[{id,name,type,maximum}]}],shockers:[{id,name,service,maximum,durationMs}]}`. Limits are 32 toys/eight functions each/256 total functions and 32 shockers, plus packet/name bounds. Device/function IDs are random 128-bit session aliases, never hardware IDs, saved local keys or provider credentials. Only locally owned inventory is advertised. Supported non-setting scalar capabilities are shared; unknown/depth/position are rejected. Remote shocker metadata prepares the later tab; it is separate from Toy control inventory.
- `state`: complete array of `{device,channel,percent,claim}` at approximately 30 network frames/sec. Percent is integer 0–100. Omission ends that channel's peer lease. All targets must exist in the current owner's advertised map; invalid/unknown/duplicate entries reject the entire snapshot. A fresh gesture/Play allocates a newer per-function claim. Existing claims only renew their exact `LocalToyController` source lease within remaining freshness. Owner edits/Stop, expiry and failed updates block the old claim; late traffic cannot reclaim it. Receiving hardware rate/native quantization remains independent.
- `result`: rejected `{device,channel,percent,claim}`, invalidating the sender's matching source/loop without taking over unrelated functions. Version 0.7.5 adds optional `reason`: `input-expired`, `other-input`, `owner-or-safety-reset`, `controller-changed`, `controller-unavailable` or `old-claim`. Older receivers/senders ignore this additive field; missing/unknown text becomes a fixed generic diagnostic, never raw peer text. It grants no permission and changes no output gate. From 0.7.3, connected remote rows retain the user's selection when invalidated. The affected loop/capture stops, held desktop/touch/pointer input must release, and only fresh drawing/Play can claim again. Selection does not renew or replay output. Explicit Stop all still clears selection; disconnect removes the remote inventory.
- `stop`: ends only incoming peer-owned leases. Local owner Stop remains authoritative over all local output. Disconnect clears both session directions and all remote inventory/activity.
- `shock`: `{commandId,device,type,percent,durationMs}`. A session-bounded deduplication set rejects repeats; no physical retry, continuous shock curve or reconnect replay exists. The owner translates only current session aliases, retains remaining expiry through local IPC, and uses other-controller caps/pause/cooldown/provider permissions. Shocker control uses this interface for discrete buttons and the two-step Shock confirmation.

The private remote child uses redirected JSON-line pipes, no provider keys, UI heartbeats, bounded queues and a kill-on-owner-close Windows job. Local IPC `{kind:'send',type,payload,createdAt}` preserves original snapshot age. The existing shocker bridge adds owner-local `remoteGate {session}` and `remoteControl {session,key,type,intensity,durationMs,expiresAt}`; only a matching nonempty active gate and fresh expiry permit a submission. Configuration/migration/token storage and existing owner controls remain unchanged. The app's Connect page is session-only; no Connect-on or activity is restored from disk.

Proof so far is software/native-package/public-helper testing between two processes on one Windows host with simulated hardware. Separate internet networks, physical toy/shocker timing and device/PC-failure stopping are not verified.

Version 0.7.5 adds private worker `health` events every five seconds with numeric state-send/receive/drop/backpressure counters, maximum age/gap/RTT/clock uncertainty and minimum remaining lifetime. Only these known numeric fields enter the app's rate-limited REMOTE log; no packet, identity, endpoint or code is logged. Receiver rejection logs include previous accepted-state timing and the app tick gap. Copy remote log filters the existing session log and adds version/capture time. This is diagnostic IPC only; network message version, state/shock freshness, ownership, Stop, no replay and credentials are unchanged.

## Implemented local OpenShock activity notices (2026-10-11)

The bridge adds stdout lines `@activity {"kind":"shocker-activity","key":"...","id":"...","phase":"...","remainingMs":...}` for the app's active-output closing warning. `key` is an existing configured card key. `id` is a fresh operation UUID, never the hardware UUID or API log ID. Phases are `pending` before a real live HTTP dispatch (command duration plus the existing eight-second request timeout), `accepted` after success (bounded command duration), `rejected` for definitive 4xx other than 408, and `uncertain` for ambiguous failures (bounded command duration, no retry). Storage is bounded to 256 devices and 256 pending operations per device, with a conservative bounded deadline on overflow. Session-only monotonic deadlines survive bridge exit/restart until expiry. Stale initial history remains skipped. These are observations for a warning, not acknowledgement of radio delivery or physical power. Existing JSON stdin commands, owner limits, no retry/replay and remote protocol below remain unchanged.

`disconnected -> connecting -> paired -> authorized/paused -> armed -> streaming`

Permission revocation, local stop, transport failure, or input expiry closes the output gate. Reconnection establishes a fresh session generation and starts paused. It never restores physical output merely because the network reconnected.

Both directions negotiate separate grants. A successful connection and knowledge of a room ID do not grant control. Invitations should be unpredictable, time-limited, and single-use; authenticate the intended peer and bind the invitation to the WebRTC peer identity/fingerprint.

## Negotiation

Exchange protocol version, supported message types, requested shares, and session-scoped channel descriptors. The owner accepts a subset and assigns the final channels and limits.

Each channel identifies exactly one device capability. Initial remote physical support is continuous vibration. Unknown capabilities and incompatible versions are rejected explicitly.

Negotiate frame frequency and limits on message size/channel count. Treat all inbound messages as untrusted. Validate type, finite numeric values, lengths, range, ownership, generation, and authority before routing.

## Message families

| Family | Intended channel | Required semantics |
| --- | --- | --- |
| hello / capabilities | Reliable | Version and capability negotiation |
| grant / revoke / arm / disarm | Reliable | Owner authority, grant revision, acknowledgement |
| state | Fast, unordered, without retransmitting superseded frames | Complete current snapshot, sequence, freshness, grant revision |
| pattern upload / start / stop | Reliable | Bounded content, hash/version, command ID, expiry, acknowledgement |
| stop | Reliable plus fast duplicate where available | Idempotent stop/disarm; receiver clears pending output and invalidates the old output generation |
| status / acknowledgement | Reliable or bounded telemetry as appropriate | App receipt / adapter acceptance / hardware observation must be distinguishable |

A reliable channel cannot guarantee prompt delivery during a network outage. Local stop and the receiver watchdog do not wait for it.

## Example live-state envelope

Readable JSON for discussion; binary encoding may be selected after measurement.

```json
{
  "version": 1,
  "kind": "state",
  "sessionId": "example-session",
  "generation": 2,
  "grantRevision": 3,
  "sequence": 1042,
  "sentAtMs": 41235,
  "validForMs": 250,
  "values": [
    { "channelId": "shared-vibrator-1", "value": 0.35 },
    { "channelId": "shared-vibrator-2", "value": 0.60 }
  ]
}
```

Version 1 above is a proposed first implementation envelope; the document remains a 0.1 draft. Session timing is monotonic, not an assumed shared wall clock.

Estimate clock offset and uncertainty during setup. Sequence numbers reject duplicates/older frames; they do not by themselves prove freshness. Reject frames whose useful lifetime has passed. Enforce both per-frame freshness and a receiver-local timeout based on accepted fresh frames.

An omitted negotiated channel in a complete snapshot becomes zero. An unknown or unauthorized channel must never control hardware. Define atomic rejection versus per-channel rejection before shipping; use atomic rejection for the first version.

## Queues and timing

Starting targets to test, not promised performance:

- 30-60 complete network frames/second.
- Small binary batches, with a bounded size suitable for the negotiated transport.
- One replaceable pending live snapshot per session, plus bounded reliable command queues.
- Initial state lifetime around 250 ms and local output timeout around 300-500 ms, tuned together after measurement.
- No uncontrolled extrapolation, backlog replay, or smoothing that delays stop.

Clock uncertainty or unusually high network delay may require a more conservative configured mode. Record the actual failure behavior rather than silently increasing timeouts.

## Command processing

Commands carry `commandId`, session generation, grant revision, and expiry. Acknowledge accepted/rejected/expired status with the same ID. Use bounded deduplication so a repeated pattern-start request cannot start multiple patterns.

Never execute expired actions. Never replay missed actions after reconnect. Network acknowledgement/retry policy must not become automatic retries of existing OpenShock physical commands.

Stop closes the output gate, clears queues/patterns, and invalidates the previous output generation. Old state cannot restart a toy. Re-arming is explicit and owner-authorized.

## Pattern playback

Upload bounded patterns reliably, verify the complete content, then start locally with agreed timing. Define stop, duration, maximum levels, and interruption by local owner controls. Pattern transfer and playback cannot monopolize the live channel.

## Telemetry

Report connection method (direct or relayed), round-trip time, jitter/update age where measurable, dropped/expired frames, queue pressure, adapter connection, and separately measured hardware command rate.

Do not label an acknowledged network packet as confirmed physical movement. Avoid logging payload secrets, raw hardware identifiers, or full invitations.
